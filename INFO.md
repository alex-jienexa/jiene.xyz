## Общая архитектура проекта

Проект является классическим *клиент-серверным приложением*. 
Сторона клиента (фронтенд на `Solid.js`) посылает запросы к стороне сервера (бекенд на `Chi`), который в свою очередь получает и записывает данные в базу данных (`PostgreSQL`) и возвращает клиенту ответ в формате JSON.
 
Важно отметить наличие двух режимов работы:
- **Dev-режим** - фронтенд и бекенд запущены отдельно.
Они связаны друг с другом через CORS и Vite-прокси для пути `/api`.
Также для приложений настроен hot-reload, чтобы можно быстро обновлять приложение при сохранении файлов репозитория (для фронтенда это настроено автоматически, а для бекенда - через `air`).
- **Prod-режим** - при запуске такого режима, фронтенд автоматически собирается (`bun run build`) и результаты сборки отправляются в директорию `backend/internal/static/{dist}` (см. `/Dockerfile`).
Так, приложение будет представлять лишь бекенд-контейнер и базу данных, следовательно, не требуется настройка прокси между компонентами.

Каждый режим запускается с помощью разных Docker Compose файлов (см. `/docker-compose*.yml`):
```sh
docker compose -f docker-compose.dev.yml up # Для Dev-режима
docker compose up # Для Prod-режима
```
Однако, также имеется возможность работы с `make` для более удобного CLI-взаимодействия (см. `/Makefile`):
```sh
make dev # Для Dev-режима
make prod # Для Prod-режима
```

Стоит обратить внимание и на теги сборки go-приложения, которые определяют принцип работы со статическими файлами. 

## Бекенд - чистая архитектура

Обратимся к теории:
> Чистая архитектура, или Clean-architecture - это принцип разделения структуры приложения (не только директории, но и классы) по слоям.
> Выделяют следующие слои:
> - `entity` - описание стркутур данных. Зачастую это таблицы в базе данных (и их программное представление коде для работы с ними).
> - `repository` - это интерфейсы для структур и реализация доступа к данным из БД (могут быть каждый репозиторий для каждой СУБД - достаточно важная деталь).
> - `service` - бизнес-логика, работающая с репозиториями структур. Если без тупых слов, то это методы обработки готовых сценариев работы со структурами. То есть это слой, где идёт самая основная работа. Причём обрабатываться могут несколько структур данных: если добавляется новый пост (допустим это сущность `Post`), то добавляются все уведомления пользователям, кто подписался на автора (идёт работа с `Profile` пользователей, подписанных на `Profile` автора).
> - `handler` - предоставляет различные HTTP-хендлеры для фронтенда и на их вызов вызывает бинес-логику сервисов. Максимум, что может делать ещё - парсить запрос пользователя, и то я могу ошибаться.

Архитектура бекенда строится именно на чистой архитектуре и далее проведём разбор всех её компонентов.

*Примечание: Далее в этой главе (да и в других главах про бекенд) под путями я буду подразумевать путь относительно `/backend/`.*
*То есть, если вы видите путь `cmd/`, то вы должны подразумевать путь `/backend/cmd/`.*

### Слой `entity`

Она реализована в директории `internal/entity/`. 
Здесь описаны структуры данных.
Это может быть то, что хранится в базе данных, а также то, что приходит или уходит от API.
В Golang это имеет вид структур (тип `struct`):

```go
type Profile struct {
	ID        int             `db:"id"`
	Name      string          `db:"name"`
	Alias     string          `db:"alias"`
	Role      string          `db:"role"`
	Status    string          `db:"status"`
	Tags      json.RawMessage `db:"tags"`
	Links     json.RawMessage `db:"links"`
	UpdatedAt time.Time       `db:"updated_at"`
}
```

При этом имеется некоторые важные детали, которые делают из "хранение одной структуры" в довольно динамичное разделение.

#### Разделение структуры по задачам
Посмотрим на сущность `Article` и её структуры.
Стоит обратить внимание на то, что для каждой задачи имеется своя структура.
```go
type Article struct { } // Структура статьи, которая хранится в БД
type ArticleListItem struct { } // Структура статьи как элемент списка
type ArticleCreateInput struct { } // Структура-шаблон для созрания статьи с помощью API
type ArticleUpdateInput struct { } // Структура-шаблон для обновления статьи с помощью API
type ArticleFilter struct { } // Поля из статьи, доступные для фильтрации при поиске статей
```
Так, вместо одной структуры для статей имеется 5 структур для каждой задачи: одна для БД (обратите внимание на пример выше - там стоят теги `db:...`, что отражают связь с БД), вторая для перечислений (без содержания статьи), ещё два для изменения структуры и один для фильтрации. 
Это позволяет более точно управлять контентом и не заставлять другие слои проверять данные на достоверность или оптимизацию.

#### Наличие указателей
Не уходя из `Articles`, обратим внимание на структуры создания и обновления статьи:
```go
type ArticleCreateInput struct {
	Slug      string         `json:"slug"`
	ProjectID *int           `json:"project_id"`
	Title     string         `json:"title"`
	Section   ArticleSection `json:"section"`
	Kind      ArticleKind    `json:"kind"`
	Content   string         `json:"content"`
	TagSlugs  []string       `json:"tags"` // ["pf2e", "ml"] — слаги тегов
}

type ArticleUpdateInput struct {
	Title       *string         `json:"title"`
	Section     *ArticleSection `json:"section"`
	Kind        *ArticleKind    `json:"kind"`
	Content     *string         `json:"content"`
	IsPublished *bool           `json:"is_published"`
	TagSlugs    []string        `json:"tags"`
}
```

Обратите внимание на типы переменных.
Когда в шаблоне создания указывается просто тип переменных, то в шаблоне обновления указываются только указатели на них.
Тут работает принцип работы типов Go (а может и других строго типизированных языках).
Дело в том, что стандартные типы данных не могут содержать пустые значения. 
Не стоит путать "нулевые" и "пустые" значения, так как для типа `int` имеется большая разница между `0` и `nil`, или `""` и `nil` для строки.
Как уже понятно, указатели позволяет передавать пустые значения, в дополнение к нулевым.
С практической точки зрения это означает, что данное поле опционально для передачи - если его не нужно менять, то оставьте там `nil`.

Разница тут принципиальная:
- `Title: ""` - изменить заголовок на пустую строку;
- `Title: nil` - не менять заголовок.

С помощью JSON (и без указателей) отследить такие отличия просто невозможно.
Пользователю пришлось бы просто переписывать старые значения (или фронтенду автоматически их подставлять в поля), чтобы оставить поле без изменений.
Указатели, как роль опциональных полей, решает данную проблему.

#### Отсутствие идентификаторов, где они не нужны
Наверняка, когда вы смотрели предыдущий блок кода, вы задались вопросом *"а где идентификатор в шаблоне `Update`?"*
Отвечаю - его незачем передавать из фронтенда.
Точнее говоря, он и так передаётся, но в другом месте.
Идентификатор статьи (поле `slug`) получается не из шаблона, а из адреса API через query-параметры:
```go
// cmd/main.go
// ---
r.Put("/articles/{slug}", articleHandler.Update)

// internal/handler/article_handler.go
// ---
slug := chi.URLParam(r, "slug")
// вставить сборку input из тела запроса...
article, err := h.service.Update(r.Context(), slug, input)

// думаю, дальше принцип понятен
```

Если программисту известно, что эндпоинт обновления статьи будет соджержать его идентификатор (`PUT /api/articles/{slug}`), то зачем его повторно указывать в теле запроса?

#### Типизированные константы

Некоторые типы могут содержать лишь строку, например отображение, что статья имеет тип "запись" должно иметь вид `Kind: "note"`.
Это называется *magic string* - строки, которые играют роль типа данных.
Недостатком такого метода является возможность опечатки или написания той строки, которая не является частью возможных разрешённых строк.
В Go эта проблема решается с помощью типизированных констант:
```go
type ArticleKind string
const (
	KindArticle  ArticleKind = "article"
	KindDevlog   ArticleKind = "devlog"
	KindResearch ArticleKind = "research"
	KindNote     ArticleKind = "note"
	KindEssay    ArticleKind = "essay"
)
```
Так, вместо того чтобы писать `Kind: "note"`, нужно теперь писать `Kind: KindNote`.
А проблема проверки разрешённость строк решается за вас компилятором - достаточно указать созданный тип как тип данных в поле структуры.
```go
type Article struct {
	// ...
	Kind        ArticleKind    `db:"kind"`
    // Получается, что статья имеет строгие строки, указанные в константах `Kind..`
}
```
При этом вне Go (то есть в JSON или БД) значение автоматически заменится на строку.

*Примечание: в решениях на других языках программирования привлекают к использованию перечислений (`Enum`).*
*Однако, в Go нет таких типов, что прибегает к использованию таких "костылей".*

#### Доменные ошибки
В `internal/entity/errors.go` имеется перечисление основных HTTP-ошибок:
```go
var (
	ErrNotFound      = errors.New("resource not found")
	ErrAlreadyExists = errors.New("resource already exists")
	ErrInvalidInput  = errors.New("invalid input")
	ErrUnauthorized  = errors.New("unauthorized")
)
```
Тут соблюдается ключевая идея чистой архитектуры.
Так как слои не должны знать о том, что происходит на слоях выше, то слои репозиториев и сервисов не должны знать, что они используют HTTP для ошикок.
Однако, оставлять программисту слоя хендлеров разбирать все ошибки прошлых слоёв будет достаточно неудобно, и именно поэтому и реализуется такая структура. 

Так, слои могут использовать такие абстрактные ошибки, а уже handler просто их проверять через `errors.Is(err, entity.Err*)` и возвращать нужный HTTP-ответ.
Так, принцип чистой архитектуры не нарушается - ведь связь слоёв идёт вниз, а сущности находятся на самом низу отношений. 

### Слой `repository`

Слой репозиториев реализован в `internal/repository/`.
Основной ролью данного слоя является реализация методов использования сущностей, а также их управление (получение/сохранения) с различными базами данных.
В качестве основного драйвера был выбран PosgreSQL как наиболее популярная и удобная реляционная база данных.

Для каждой сущности реализуется два вида файлов:
- `xxx_repository.go` - интерфейс репозитория (то есть контракт на то, какие методы должны быть);
- `xxx_repository_pg.go` - реализация интерфейса для драйвера Posrgre.

Следовательно, слой сервисов будет зависеть не от реализации интерфейса, а от него самого, чтобы при смене драйвера не переписывать приложение.
Собственно, когда появится другой драйвер, необходимо лишь заменить создаваемый тип данных в `cmd/main.go` или при определении репозитория:
```go
// internal/repository/profile_repository_pg.go
// ---
func NewProfileRepository(db *sql.DB) ProfileRepository {
	return &profilePostgresRepository{db: db} // <- вот тут просто заменить тип реализации на нужный
}

// cmd/main.go
// ---
profileRepo := repository.NewProfileRepository(db) // <- ...или тут

// ---
// Тут, правда, замечается небольшой антипаттерн, так как мы определяем "основной" репозиторий прямо внутри реализации интерфейса.
// По-хорошему мы должны создать отдельный файл, состоящий из определений репозиториев для каждой сущности и менять его там.
// Тем не менее, пока имеется только один репозиторий, это не так критично.
```
Как уже и было сказано, слой сервисов не будет зависеть от реализации бд и никак не будет меняться, если драйвер будет заменён на другой в процессе разработки.

#### Динамичное построение SQL-запроса под фильтры
В репозитории статей (`internal/repository/article_repository_pg.go`) имеется метод `List()`, возвращающий список статей.
Так как SQL сильно зависит от построения запроса, а у нас имеется возможность пропускать некоторые вводы фильтров, то требуется динамическое построение запроса.
При этом важно уследить за тем, чтобы не было возможности SQL-инъекции в коде.

Так, проверяется каждый вид фильтров и составляется массив из определённых фильтров выбора, например:
```go
// Массив SQL-условий. Изначально там располагается фильтр "только опубликованные статьи".
conditions := []string{"a.is_published = true"}
// Массив аргументов к фильтрам
args := []interface{}{}
// Позиция первого аргумента после перечисления фильтров. Чисто технически можно просто посчитать через `len(args)`, однако хранение числа будет выгодней по оптимизации.
argPos := 1

// Если задана секция...
if filter.Section != "" {
    // ...добавим условие, связано с секцией...
    conditions = append(conditions, fmt.Sprintf("a.section = $%d", argPos))
    // ...добавим его значение как аргумент...
    args = append(args, filter.Section)
    // ...и увеличим счётчик позиции.
    argPos++
}
```
После всего перечисления строится итоговое условие в ключевом слове `WHERE`:
```go
whereClause := strings.Join(conditions, " AND ")
```

Далее идёт небольшой код с запросом для получения общего количества статей и параметров количества статей на экране (посмотрите сами, тут важно понимать что их результат будет в переменных `limit` и `offset`).
После этого идёт составление итогового запроса:
```go
// Составляем итоговый запрос
listQuery := fmt.Sprintf(`
    SELECT a.slug, a.title, a.section, a.kind, a.is_published, a.published_at, p.slug, LENGTH(a.content)
    FROM articles a
    LEFT JOIN projects p ON p.id = a.project_id
    WHERE %s
    ORDER BY a.published_at DESC
    LIMIT $%d OFFSET $%d
`, whereClause, argPos, argPos+1)

// Добавляем переменные после подсчёта
args = append(args, limit, offset)

// Выполняем запрос, подставив нужные переменные
rows, err := r.db.QueryContext(ctx, listQuery, args...)
```

Может показаться, что в такой реализации может быть SQL-инъекция.
Однако, это ошибка, ведь передача переменных через `$x` (их называют ещё "плейсхолдерами") предотвращает такие действия, а код гарантирует, что при подстановке через `fmt.Sprintf` попадают только строго прописанные в коде строки, а не данные пользователя.
Именно поэтому существует массив `args` - чтобы не подставлять данные через `Sprintf`, а через плейсхолдеры.
